# 任务要求

> 题目冻结区，确认后不再随意改；和导师沟通后有调整，在此记录变更日期和原因。

## 一、最低完成要求

1. 完整系统：Android App（Java）+ 服务端（Spring Boot）+ 数据源（ESP8266；硬件受限时可用可配置数据模拟器，但论文里要说明，并保证协议链路是真实的）。
2. 通信链路：打通终端—通信—服务端—显示整条链路，不能停留在"能采集、能上传、能显示"这种浅层功能。
3. 数据管理：服务端存历史数据，App 能看实时数据和历史数据。
4. 核心机制（论文核心章节）：MQTT 与 HTTP 两种通信机制的定量比较。App 同时实现 MQTT 订阅和 HTTP 轮询两条通道。
5. 对比实验（控制变量）：开始对比前固定以下变量并在论文里写清楚——
   - 上报频率和 HTTP 轮询间隔取同一数值（1s / 5s / 30s）
   - payload 大小
   - 网络环境（局域网 / 弱网）
   - 服务端处理逻辑
   - 是否长连接
   - MQTT 的 QoS 等级
   每项指标在三种频率下各测不少于 30 次，报告均值与最大值。
6. 定量性能测试：端到端延迟、消息到达率/丢包率、控制指令响应时延（单独测）。
7. 异常工况：断网恢复实验，记录两种机制的恢复时间和是否丢数据。
8. 结论：落到"什么场景选什么机制"，不能笼统说谁快。
9. 完整毕业论文，按学校格式。

## 二、拓展目标（时间允许再做）

- 数据可视化增强（历史曲线、多指标同屏）
- 多设备管理（多个 ESP8266 节点接入）
- 缓存/消息可靠性（断网本地缓存、自动重连、补传）
- 手机耗电统计（Android 系统级统计误差较大，只作参考，不作核心结论）

## 三、降级方案（时间实在不够时的兜底）

保留"实时数据显示 + 远程控制 + 报警"三个基本功能；历史查询、多设备管理可以不做。
但 MQTT 与 HTTP 的定量对比不能删——删了论文就没有专业深度。
