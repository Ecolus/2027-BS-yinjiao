# 任务要求（最低完成要求 + 拓展目标）

> 本文件为题目冻结区，确认后不再随意改动。如与导师沟通后调整，需在此记录变更日期与原因。

## 一、最低完成要求（必须全部达成）

1. **完整系统**：Android App（Java）+ 服务端（Spring Boot）+ 数据源（ESP8266 现成传感器模块直接上报；硬件受限时允许使用可配置数据模拟器，但必须在论文中说明并保证协议链路真实）。
2. **通信链路**：打通终端—通信—服务端—显示的完整链路，不允许停留在"能采集、能上传、能显示"的浅层功能。
3. **数据管理**：服务端存储历史数据，App 支持实时数据与历史数据查看。
4. **核心专业机制（论文核心章节）**：MQTT 与 HTTP 两种通信机制的定量比较。App 同时实现 MQTT 订阅与 HTTP 轮询两条数据通道。
5. **对比实验（控制变量）**：对比前必须固定并在论文中写明：
   - 上报频率与 HTTP 轮询间隔（两者取同一数值，如 1s / 5s / 30s）
   - payload 大小
   - 网络环境（局域网 / 弱网）
   - 服务端处理逻辑
   - 是否长连接
   - MQTT 的 QoS 等级
   在此基础上，每项指标在三种频率下各测不少于 30 次，报告均值与最大值。
6. **定量性能测试**：
   - 端到端延迟
   - 消息到达率 / 丢包率
   - 控制指令响应时延（单独测）
7. **异常工况测试**：断网恢复实验，记录两种机制的恢复时间与是否丢数据。
8. **结论要求**：落到"在何种场景下应选哪种机制"，而不是笼统说谁快。
9. **完整毕业论文**：按学校格式完成。

## 二、拓展目标（时间允许时做）

- 更丰富的数据可视化（历史曲线、多指标同屏）
- 多设备管理（多个 ESP8266 节点统一接入）
- 缓存 / 消息可靠性机制（断网本地缓存、自动重连、数据补传）
- 手机耗电作为拓展指标（Android 系统级统计误差较大，仅作参考，不作核心结论）

## 三、降级方案（时间实在不足时的兜底）

保留"实时数据显示 + 远程控制 + 报警"三项基本功能即可；历史查询与多设备管理可以不做。
**但 MQTT 与 HTTP 的定量对比不能删**——否则论文没有专业深度。
